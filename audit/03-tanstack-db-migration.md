# Part 3 — Re-architecture Plan: TanStack DB + Supabase Collections

## Re-scoping this part, per the ground rules

The prompt this audit was run against assumes the starting point is "should we adopt TanStack DB." **That has already happened.** Per `00-discovery.md` §7 and confirmed by reading all seven collection files in `packages/api-client/src/collections/`, the app already uses `@tanstack/react-db` (`createCollection`) with `@tanstack/query-db-collection`'s `queryCollectionOptions` — a TanStack-Query-backed adapter wrapping hand-written `fetch()` calls to the Hono API (`services/core`). No Supabase-specific TanStack DB adapter package exists anywhere in `bun.lock`, and no Supabase Realtime channel subscriptions exist anywhere in the client code (grep for `.channel(` / `supabase.channel` / `postgres_changes` in `apps/web/src`, `packages/api-client/src`, `packages/lib/src`: zero matches).

So the real question this part answers is narrower and more consequential than the prompt assumed: **should the existing REST-backed collections be re-pointed at Supabase directly (via a Supabase collection adapter, direct `supabase-js` queries, and/or Realtime), and is now the right time** — not "should TanStack DB be adopted at all."

**The answer, given what `01-architecture.md` §1.5 found, is: not yet, and not before a specific prerequisite is fixed.** `services/core` has zero authentication and zero organization-scoping enforcement today; the API returns every organization's entire dataset to any anonymous request. Moving the client to query Supabase's Postgres directly would only be *safe* if Row-Level Security policies fully replace what the (currently nonexistent) API-layer authorization was supposed to do — and per `00-discovery.md` §4, RLS is enabled on every table with **zero policies defined**, which today means either "deny everything" (if a client used the anon/authenticated key) or "bypass everything" (if it used the service-role key, which must never ship to a browser). Migrating to a Supabase collection adapter without first writing real RLS policies would mean shipping the same unscoped-data-exposure problem in a different, harder-to-audit place (declarative SQL policies scattered per table, instead of one Hono middleware). This plan is written with that constraint as the controlling fact.

## 1. Current data layer audit

All seven collections (`events`, `users`, `organizations`, `org-memberships`, `event-members`, `attendance`, `loyalty` — `packages/api-client/src/collections/*.ts`) follow one uniform, mechanically-generated-looking pattern:

- **Reads:** `queryFn` does a bare `fetch(${getAPIBaseURL()}/<resource>)` with **no query parameters, no pagination, no organization scoping** — every collection loads the entire table on every collection instantiation. Confirmed live in this session: an anonymous page load triggered `select * from organizations order by createdAt desc` and `select * from events order by startTime desc` with no `WHERE` clause at all (`01-architecture.md` §1.5).
- **Writes:** `onInsert`/`onUpdate`/`onDelete` each issue a plain `fetch()` with method `POST`/`PUT`/`DELETE` against the same REST resource. TanStack DB's own transaction model provides the optimistic-UI behavior here for free (the mutation is applied to the in-memory collection immediately, then rolled back if the `onX` handler rejects) — this is **already real optimistic-update handling**, not something to build from scratch; it just isn't Supabase-specific.
- **Cache invalidation:** implicit and automatic — each collection shares one `QueryClient` (passed in as `queryClient` at construction) and keys itself with a fixed `queryKey` (e.g. `['events']`). TanStack Query's normal invalidation/refetch behavior applies; there's no manual invalidation code anywhere, which is appropriate for this simple a query-key scheme (one key per whole table) but wouldn't scale as-is once queries need to be parameterized (e.g. by `organizationId`, once §prerequisite above is fixed).
- **Error handling is inconsistent within the collections themselves**, already flagged in `01-architecture.md` §7: `events.ts`'s `onInsert` uses the shared `handleAPIErrors` helper (parses the API's structured error body), but its own `onUpdate`/`onDelete` — and every `onUpdate`/`onDelete` in every other collection file — throw a flat, uninformative `Error('Failed to update X')`/`Error('Failed to delete X')` without reading the response body. This should be fixed regardless of what happens with Supabase, since it affects every collection today.
- **Realtime:** none. No collection re-fetches on any event other than a manual mutation or a component remount; there is no live-update behavior (e.g., another user checking in doesn't update anyone else's `/events` or `/checkin` view without a manual refresh/re-navigation).

## 2. Domain entity → collection mapping

The mapping already exists 1:1 (schema table → TanStack DB collection); the table below is what would change under a Supabase-adapter migration, not a new mapping to invent.

| Entity (schema table, `00-discovery.md` §5) | Current collection | Current sync strategy | Proposed sync strategy if migrated | Notes |
|---|---|---|---|---|
| `organizations` | `createOrganizationCollection` | One-shot fetch, full table, no scoping | Live query scoped to the caller's `org_memberships`, via RLS | Small table, low write frequency, low realtime value — a good low-risk pilot (§4). |
| `org_memberships` | `createOrgMembershipCollection` | One-shot fetch, full table | Live query scoped to `userId = auth.uid()` OR same-org membership (needs an RLS policy that itself queries `org_memberships` — a self-referential policy, doable but worth getting right in isolation first) | This table **is** the authorization model (`role` enum) — its own RLS policy design is the crux of the whole prerequisite; do this one first and prove it before touching anything else. |
| `events` | `createEventCollection` | One-shot fetch, full table, `status` derived client-side from `startTime` (`getStatus()`, `packages/api-client/src/collections/events.ts:12-16`) | Live query scoped by `organizationId` (needs the same org-membership check) | Real realtime value here (organizers watching event state live) — but also the screen with the most vertical layout risk per `02-ui-forensic.md`, so sequence design fixes and data-layer changes independently, not in the same PR. |
| `event_members` | `createEventMemberCollection` | One-shot fetch, full table | Live query scoped by `eventId` (join to `events.organizationId`) | |
| `attendance` | `createAttendanceCollection` | One-shot fetch, full table | **High realtime value, high risk** — this is the check-in flow, the product's core transactional path (`01-architecture.md` §6). Live sync here is the single most product-relevant reason to consider Supabase Realtime at all. | Needs the most testing of anything in this table before going live, given it's also currently the least-tested flow in the app (zero tests, `01-architecture.md` §6). |
| `loyalty` | `createLoyaltyCollection` | One-shot fetch, full table | Live query scoped by `organizationId`/`patronId` | Low urgency — points/rewards data tolerates staleness far better than attendance does. |
| `users` | `createUserCollection` | One-shot fetch, full table (!) | **Do not expose as a live, broadly-queryable collection under any adapter.** Returning every user row (`email`, `firstName`, `lastName`, `phone`) to any authenticated session, scoped only by "is a member of some org," is a PII exposure risk regardless of REST-vs-Supabase. Needs its own narrower, purpose-built query (e.g. "users visible to me because they share an org") rather than a general `users` collection. | This is a data-modeling fix independent of the migration question — flagging it here because a Supabase live-query collection would make the existing over-fetch *more* visible/exploitable (a persistent live subscription vs. a one-shot fetch), not less. |

## 3. Interaction with ephemeral/pre-persistence state

`00-discovery.md`/`02-ui-forensic.md` established the one ephemeral-identity mechanism in this app: **anonymous Supabase Auth sessions** (`supabase.auth.signInAnonymously()`, `packages/lib/src/supabase/auth.ts:18`), intended (per the code comments in `apps/web/src/hooks/index.tsx:82-90`) to be the default first-visit experience, though `02-ui-forensic.md` found that path is currently non-functional due to a `manual` default-value bug. There is **no separate custom pre-persistence cache layer** in this codebase (no local-first store, no offline queue, no IndexedDB-backed draft state) — the only "ephemeral, not-yet-committed" state is the anonymous auth session itself and whatever's currently held in each TanStack DB collection's in-memory optimistic-mutation buffer.

This matters for a Supabase-adapter migration in one specific way, worth designing deliberately rather than defaulting into:

- **An anonymous Supabase user is a real row in `auth.users`** (`is_anonymous: true`), not a client-only construct — it already has a stable `auth.uid()`. That means RLS policies written against `auth.uid()` work identically for guest and registered sessions without special-casing, **as long as the app's own tables (`users`, `org_memberships`) get a row created for the guest at sign-in time** — which, per `00-discovery.md` §5, they currently don't: the `users` table has no linkage to `auth.users` visible in the schema, and no code path found in this session inserts a `users` row on anonymous sign-in. **This is the actual handoff point that needs designing**, not a TanStack DB concern per se: decide whether a guest gets a `users` row immediately (simpler RLS, but creates DB rows for every anonymous visitor, including ones who bounce) or only at conversion time (per `05-user-management-upgrade.md`'s analysis of the `/upgrade` screen, which is really the guest→registered conversion form) — and until that's decided, no collection that joins through `users` (which is most of them, per §2's relations) can be safely scoped by RLS for a guest session.
- **Don't force this into a TanStack DB collection for its own sake.** The anonymous session token itself is Supabase Auth's concern (already handled by `supabase-js`'s own storage), not application data — there's no reason to wrap it in a collection, and doing so would just be architectural purity for no functional gain, which the audit brief specifically warns against.
- **In-flight optimistic mutations reconciling with a just-converted account:** today, a guest's TanStack DB collections are all fetched fresh per page load (no persistence across sessions), so there's no cross-session optimistic-mutation reconciliation problem to solve yet. If Supabase Realtime/live queries are introduced later, the reconciliation moment is exactly the guest→registered conversion (the `/upgrade` flow) — any in-flight mutation at that moment should be allowed to complete against the *same* `auth.uid()`, since Supabase's anonymous-to-permanent upgrade (`supabase.auth.updateUser()` linking an email) preserves the user's `auth.uid()` rather than issuing a new one. This is a reason to prefer that Supabase upgrade path over the current `/upgrade` screen's implementation (a separate "Create account" form, `02-ui-forensic.md`) — worth cross-referencing in `05-user-management-upgrade.md`.

## 4. Migration sequencing (only after the prerequisite)

**Prerequisite, blocking, sequenced before phase 1:** write real RLS policies for at least `organizations` and `org_memberships`, matching the `owner/admin/member/viewer` role model that already exists as data (`00-discovery.md` §5) but is enforced nowhere (`01-architecture.md` §1.5). This is `01-architecture.md`'s priority-0 fix, restated here because it's also this migration's precondition — the same piece of work unblocks both.

| Phase | Scope | What changes | Rollback |
|---|---|---|---|
| **0 (prerequisite)** | `organizations`, `org_memberships` RLS policies only; no client changes | Write and test Postgres RLS policies against these two tables using a real Supabase client with the anon/authenticated key (not the service-role key `services/core` currently uses) — verify a user can only see orgs they belong to. No app code changes yet. | N/A — additive, doesn't touch the running app. |
| **1 (pilot)** | `organizations` collection only, in `apps/web`'s `/organizations` screen | Swap `createOrganizationCollection`'s `queryFn`/sync from the REST fetch to a Supabase-backed query (direct `supabase-js` `.from('organizations').select()` under RLS, or a Supabase TanStack DB adapter once one is evaluated/selected). Chosen as the pilot because: it's the lowest-write-frequency, lowest-realtime-value entity (§2), and per `02-ui-forensic.md` it's already the one screen surfacing plan/tier data — a natural place to validate RLS-based scoping visually (a user should only ever see their own orgs' plan badges). | Feature-flag the data source per collection (REST vs. Supabase) behind a single config value; flip back to REST if RLS policies produce wrong results. Both paths can coexist since both ultimately read the same Postgres tables. |
| **2** | `org_memberships`, `events`, `event_members` | Extend RLS policies to cover the join-heavy tables; migrate their collections once phase 1's approach is validated in production for a defined soak period (propose 2-4 weeks, adjustable once real usage data exists — flagged as unmeasurable from static analysis alone). | Same per-collection flag mechanism. |
| **3** | `attendance` | The highest-value, highest-risk entity for Realtime (§2) — migrate last, after the check-in flow has actual test coverage (`01-architecture.md` §6 priority #7), not before. | Same mechanism; additionally keep the REST path as the documented fallback for check-in specifically, since it's the core transactional flow and cannot tolerate an unvalidated new failure mode. |
| **Not planned** | `users`, `loyalty` | `users` per §2's PII-exposure note needs its own query redesign before any adapter matters; `loyalty` has no urgency (§2) and can stay on REST indefinitely without cost. | N/A |

Each phase keeps the existing `@tanstack/react-db` + `packages/api-client` structure intact — only the sync strategy inside each `create<X>Collection` function changes. This is deliberately incremental at the *collection* level (matching how the codebase is already organized) rather than a per-screen or big-bang rewrite.

## 5. Risk register

- **RLS/authorization gap (§ prerequisite) — the dominant risk.** Everything else in this list is secondary until this is closed; migrating to Supabase before fixing it would functionally relocate today's data-exposure bug into RLS policy code instead of removing it.
- **Realtime subscription cost/connection limits at scale.** Cannot be assessed from static analysis — Supabase's Realtime pricing and connection ceilings scale with concurrent client connections, which depends on real usage patterns this audit has no access to. Flagged per the ground rules as something to measure (e.g., via Supabase's own project usage dashboard) rather than estimate. Given the phased plan above defers Realtime to `attendance` (phase 3) and even there only as an option, this risk is naturally deferred too.
- **Offline/optimistic-write conflict resolution.** TanStack DB's existing optimistic-mutation model (§1) already handles the common case (mutation applied locally, rolled back on server rejection); a Supabase adapter doesn't inherently improve or worsen this unless Realtime introduces concurrent-edit scenarios (e.g., two staff members checking in the same attendee) that don't exist under the current one-shot-fetch model. This becomes a real design question specifically for phase 3 (`attendance`), not before.
- **TanStack DB / adapter maturity.** The pinned versions (`apps/web/package.json`: `@tanstack/react-db@^0.1.83`, `@tanstack/query-db-collection@^1.0.6`, `00-discovery.md`) are pre-1.0 or very early 1.x for the core `react-db` package — treat the library itself as still stabilizing. No Supabase-specific TanStack DB collection adapter was found installed or referenced anywhere in this repo (`00-discovery.md` §7); evaluating one means taking on a second early-stage dependency, not just extending one already in use. This is a reason to keep phase 1 small and reversible (§4), not a reason to avoid the idea entirely.
- **Multi-tenant scoping interaction with RLS.** Covered above, but worth restating as its own risk: RLS policies that get the `org_memberships` join subtly wrong (e.g., allowing a `viewer` role to write, or leaking org B's data to an org A member through a badly-scoped join) are easy to write and hard to catch without dedicated tests — and per `01-architecture.md` §6, this codebase currently has no test coverage anywhere to catch that class of regression. **Writing tests should be a prerequisite of phase 0, not an afterthought of phase 1.**

## "Don't migrate this" list

- **`users`** — needs a narrower, purpose-built query shape before any adapter matters (§2); migrating the current shape to Supabase would make an existing over-fetch worse, not better.
- **`loyalty`** — no realtime value, no urgency; leave on REST indefinitely.
- **The anonymous-session mechanism itself** — this is Supabase Auth's job already; don't wrap it in a TanStack DB collection for architectural symmetry (§3).
- **Anything before phase 0's RLS prerequisite lands and is tested** — restated because it's the single most important scoping decision in this part.
