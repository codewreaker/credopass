# Part 3 — Re-architecture Plan: TanStack DB + Supabase Collections (Revised)


## Re-scoping this part, per the ground rules

The prompt this audit was run against assumes the starting point is "should we adopt TanStack DB." **That has already happened.** The app already uses `@tanstack/react-db` (`createCollection`) with `@tanstack/query-db-collection`'s `queryCollectionOptions` — a TanStack-Query-backed adapter wrapping hand-written `fetch()` calls straight to Supabase's PostgREST endpoint. This is already a Supabase-backed data layer, not a REST-backed one sitting in front of Supabase. No Supabase-specific TanStack DB collection *package* is installed (`bun.lock` has no `@supabase-labs/tanstack-db` or equivalent), and no Realtime channel subscriptions exist anywhere in the client code (grep for `.channel(` / `supabase.channel` / `postgres_changes` in `apps/web/src`, `packages/api-client/src`, `packages/lib/src`: zero matches) — so today's sync strategy is one-shot fetch-and-cache, not live sync, even though the data source underneath is already Supabase.

So the real question this part answers is: **should the existing hand-rolled PostgREST-`fetch()` collections be migrated onto the official `@supabase-labs/tanstack-db` adapter — which gives live queries, optimistic mutations, and automatic Realtime sync out of the box instead of hand-maintained — and is now the right time**. It is not "should TanStack DB be adopted at all," and it is not "should the client start talking to Supabase" (it already does).

**The answer is: not yet, and not before a specific prerequisite is fixed — and if anything this is more urgent under the corrected architecture, not less.** Under the original (incorrect) framing, the exposure ran through a Hono API using a service-role key server-side. Under the actual architecture, the browser is talking to Supabase's PostgREST endpoint directly with the public anon key, which means **Row-Level Security is the *only* authorization boundary that exists or could exist** — there is no backend layer to fall back on. Per the schema audit, RLS is enabled on every table with **zero policies defined**, which with the anon key means "deny everything" is the honest current behavior *if* PostgREST is correctly rejecting unauthenticated/unpolicied requests — but it also means any table where a permissive default or a misconfigured grant exists would expose the *entire* dataset to any client holding the (necessarily public) anon key, with zero code path to catch or scope it. Moving to a fuller-featured adapter (live queries, Realtime) before RLS is written wouldn't just carry the pre-existing risk forward — it would attach a persistent, standing subscription to whatever the RLS gap allows, rather than a one-shot fetch. This plan is written with that constraint as the controlling fact.

## 1. Current data layer audit

All seven collections (`events`, `users`, `organizations`, `org-memberships`, `event-members`, `attendance`, `loyalty` — `packages/api-client/src/collections/*.ts`) follow one uniform, mechanically-generated-looking pattern:

- **Reads:** `queryFn` does a bare `fetch()` straight to Supabase's PostgREST endpoint for `<resource>`, with **no query parameters, no pagination, no organization scoping** — every collection loads the entire table on every collection instantiation. An anonymous page load triggers `select * from organizations order by createdAt desc` and `select * from events order by startTime desc` with no `WHERE` clause at all, via the anon key, with no policy currently narrowing it.
- **Writes:** `onInsert`/`onUpdate`/`onDelete` each issue a plain `fetch()` with method `POST`/`PATCH`/`DELETE` against the same PostgREST resource. TanStack DB's own transaction model provides the optimistic-UI behavior here for free (the mutation is applied to the in-memory collection immediately, then rolled back if the `onX` handler rejects) — this is **already real optimistic-update handling**, not something to build from scratch. The official adapter would give the same behavior with less hand-written plumbing, not new capability.
- **Cache invalidation:** implicit and automatic — each collection shares one `QueryClient` (passed in as `queryClient` at construction) and keys itself with a fixed `queryKey` (e.g. `['events']`). TanStack Query's normal invalidation/refetch behavior applies; there's no manual invalidation code anywhere, which is appropriate for this simple a query-key scheme (one key per whole table) but wouldn't scale as-is once queries need to be parameterized (e.g. by `organizationId`, once §prerequisite below is fixed).
- **Error handling is inconsistent within the collections themselves:** `events.ts`'s `onInsert` uses the shared `handleAPIErrors` helper (parses PostgREST's structured error body), but its own `onUpdate`/`onDelete` — and every `onUpdate`/`onDelete` in every other collection file — throw a flat, uninformative `Error('Failed to update X')`/`Error('Failed to delete X')` without reading the response body. Worth fixing regardless of the adapter question, since it affects every collection today.
- **Realtime:** none. No collection re-fetches on any event other than a manual mutation or a component remount; there is no live-update behavior (e.g., another user checking in doesn't update anyone else's `/events` or `/checkin` view without a manual refresh/re-navigation) — even though the underlying data source (Supabase/Postgres) supports Realtime natively, nothing in the client currently subscribes to it.

## 2. Domain entity → collection mapping

The mapping already exists 1:1 (schema table → TanStack DB collection); the table below is what would change under a migration to the official adapter, not a new mapping to invent.

| Entity (schema table) | Current collection | Current sync strategy | Proposed sync strategy under `@supabase-labs/tanstack-db` | Notes |
|---|---|---|---|---|
| `organizations` | `createOrganizationCollection` | Hand-rolled `fetch()` to PostgREST, full table, no scoping | Adapter-managed live query scoped to the caller's `org_memberships`, via RLS | Small table, low write frequency, low realtime value — a good low-risk pilot (§4). |
| `org_memberships` | `createOrgMembershipCollection` | Hand-rolled `fetch()`, full table | Adapter-managed live query scoped to `userId = auth.uid()` OR same-org membership (needs an RLS policy that itself queries `org_memberships` — a self-referential policy, doable but worth getting right in isolation first) | This table **is** the authorization model (`role` enum) — its own RLS policy design is the crux of the whole prerequisite; do this one first and prove it before touching anything else. |
| `events` | `createEventCollection` | Hand-rolled `fetch()`, full table, `status` derived client-side from `startTime` (`getStatus()`, `packages/api-client/src/collections/events.ts:12-16`) | Adapter-managed live query scoped by `organizationId` (needs the same org-membership check); Realtime sync becomes "free" once the adapter is in place | Real realtime value here (organizers watching event state live) — but also the screen with the most vertical layout risk per the UI forensic pass, so sequence design fixes and data-layer changes independently, not in the same PR. |
| `event_members` | `createEventMemberCollection` | Hand-rolled `fetch()`, full table | Adapter-managed live query scoped by `eventId` (join to `events.organizationId`) | |
| `attendance` | `createAttendanceCollection` | Hand-rolled `fetch()`, full table | **High realtime value, high risk.** This is the check-in flow, the product's core transactional path. Realtime here — via the adapter's built-in Postgres-change subscriptions — is the single most product-relevant reason to adopt the adapter at all. | Needs the most testing of anything in this table before going live, given it's also currently the least-tested flow in the app (zero tests). |
| `loyalty` | `createLoyaltyCollection` | Hand-rolled `fetch()`, full table | Adapter-managed live query scoped by `organizationId`/`patronId` | Low urgency — points/rewards data tolerates staleness far better than attendance does; fine to leave on the hand-rolled path indefinitely. |
| `users` | `createUserCollection` | Hand-rolled `fetch()`, full table (!) | **Do not expose as a live, broadly-queryable collection under any adapter.** Returning every user row (`email`, `firstName`, `lastName`, `phone`) to any session that can reach the anon key — scoped only by "is a member of some org" — is a PII exposure risk today, independent of the adapter question. Needs its own narrower, purpose-built query (e.g. "users visible to me because they share an org") rather than a general `users` collection. | Migrating this table onto the official adapter's live-query/Realtime machinery would make the existing over-fetch *more* dangerous (a persistent subscription that pushes every future row change to every connected client, vs. a one-shot fetch), not less. Fix the query shape before considering the adapter for this table at all. |

## 3. Interaction with ephemeral/pre-persistence state

The one ephemeral-identity mechanism in this app is **anonymous Supabase Auth sessions** (`supabase.auth.signInAnonymously()`, `packages/lib/src/supabase/auth.ts:18`), intended to be the default first-visit experience, though that path is currently non-functional due to a `manual` default-value bug elsewhere in the flow. There is **no separate custom pre-persistence cache layer** in this codebase (no local-first store, no offline queue, no IndexedDB-backed draft state) — the only "ephemeral, not-yet-committed" state is the anonymous auth session itself and whatever's currently held in each TanStack DB collection's in-memory optimistic-mutation buffer.

This matters for an adapter migration in one specific way, worth designing deliberately rather than defaulting into:

- **An anonymous Supabase user is a real row in `auth.users`** (`is_anonymous: true`), not a client-only construct — it already has a stable `auth.uid()`. That means RLS policies written against `auth.uid()` work identically for guest and registered sessions without special-casing, **as long as the app's own tables (`users`, `org_memberships`) get a row created for the guest at sign-in time** — which currently they don't: the `users` table has no linkage to `auth.users` visible in the schema, and no code path found inserts a `users` row on anonymous sign-in. **This is the actual handoff point that needs designing**, not an adapter concern per se: decide whether a guest gets a `users` row immediately (simpler RLS, but creates DB rows for every anonymous visitor, including ones who bounce) or only at conversion time — and until that's decided, no collection that joins through `users` (most of them, per §2) can be safely scoped by RLS for a guest session, under the hand-rolled fetches *or* under the adapter.
- **Don't force this into a TanStack DB collection for its own sake.** The anonymous session token itself is Supabase Auth's concern already (handled by `supabase-js`'s own storage), not application data — there's no reason to wrap it in a collection.
- **In-flight optimistic mutations reconciling with a just-converted account:** today, a guest's TanStack DB collections are all fetched fresh per page load (no persistence across sessions), so there's no cross-session optimistic-mutation reconciliation problem to solve yet. Once the adapter's live queries/Realtime are introduced, the reconciliation moment is exactly the guest→registered conversion (the `/upgrade` flow): any in-flight mutation at that moment should be allowed to complete against the *same* `auth.uid()`, since Supabase's anonymous-to-permanent upgrade (`supabase.auth.updateUser()` linking an email) preserves the user's `auth.uid()` rather than issuing a new one. This is a reason to prefer that Supabase upgrade path over the current `/upgrade` screen's separate "Create account" form implementation.

## 4. What's new: `@supabase-labs/tanstack-db`

Supabase has published an official TanStack DB collection adapter under `@supabase-labs/tanstack-db` (npm; also on GitHub as `supabase/tanstack-db`), currently **alpha**. Relevant to this plan:

- It's a drop-in frontend data layer over an *existing* Supabase project — no migration of the underlying Postgres schema, RLS, or Auth setup required. That fits this codebase well: the data source doesn't change, only how collections are defined and synced.
- It provides three things the current hand-rolled collections build manually today, or don't have at all: **live queries** (components re-render on change, no manual invalidation code needed — this app currently relies on TanStack Query's default invalidation, which works but is manual/implicit rather than push-based), **optimistic mutations** (already achieved here via TanStack DB's own transaction model — the adapter doesn't add capability, it removes the need to hand-write the `onInsert`/`onUpdate`/`onDelete` fetch calls), and **automatic Realtime sync** (subscribes to Postgres changes and pushes updates to every client with a live query on that collection — this app has *none* of that today, per §1).
- It's explicitly typed against the project's schema, with collection definitions generatable via the Supabase CLI from that schema — a reasonable fit given this repo already generates/maintains typed schema artifacts elsewhere.
- Caveat worth weighing alongside the "alpha" label: it does not yet support server-side rendering (collections fetch client-side only), which matches how this app already works (client-side TanStack DB collections), so this isn't a new constraint introduced by adopting it — but it's still a very young dependency (recently launched) sitting alongside `@tanstack/react-db` itself being pre-1.0. Two early-stage dependencies stacked is a real consideration, not a blocker.

**Recommendation:** evaluate `@supabase-labs/tanstack-db` as the target for the migration phases below, in place of continuing to hand-write PostgREST `fetch()` calls per collection — but only after the RLS prerequisite (§5) lands, and starting with the same low-risk pilot collection either way. If the adapter's alpha rough edges turn out to block the pilot, falling back to the current hand-rolled-fetch pattern (which already works and is well-understood) is a reasonable interim rather than blocking the whole plan on the adapter maturing.

## 5. Migration sequencing (only after the prerequisite)

**Prerequisite, blocking, sequenced before phase 1:** write real RLS policies for at least `organizations` and `org_memberships`, matching the `owner/admin/member/viewer` role model that already exists as data but is enforced nowhere. Because the client already talks to Supabase directly with the anon key (§ re-scoping above), this is not just "this migration's precondition" — it's the only authorization layer this app has or will have, adapter or no adapter.

| Phase | Scope | What changes | Rollback |
|---|---|---|---|
| **0 (prerequisite)** | `organizations`, `org_memberships` RLS policies only; no client changes | Write and test Postgres RLS policies against these two tables using the anon/authenticated key (the same key the client already uses) — verify a user can only see orgs they belong to. No app code changes yet. | N/A — additive, doesn't touch the running app. |
| **1 (pilot)** | `organizations` collection only, in `apps/web`'s `/organizations` screen | Swap `createOrganizationCollection`'s hand-rolled `fetch()` `queryFn`/mutation handlers for `@supabase-labs/tanstack-db`'s collection helpers, under the RLS policy from phase 0. Chosen as the pilot because: it's the lowest-write-frequency, lowest-realtime-value entity (§2), it's already the one screen surfacing plan/tier data — a natural place to validate RLS-based scoping visually (a user should only ever see their own orgs' plan badges) — and it isolates the alpha-adapter risk to one collection. | Feature-flag the collection implementation (hand-rolled fetch vs. adapter) behind a single config value; flip back to hand-rolled fetch if the adapter misbehaves or RLS policies produce wrong results. Both paths read the same Postgres tables, so they can coexist. |
| **2** | `org_memberships`, `events`, `event_members` | Extend RLS policies to cover the join-heavy tables; migrate their collections to the adapter once phase 1 is validated in production for a defined soak period (propose 2–4 weeks, adjustable once real usage data exists). | Same per-collection flag mechanism. |
| **3** | `attendance` | The highest-value, highest-risk entity for Realtime (§2, §4) — migrate last, after the check-in flow has actual test coverage, not before. | Same mechanism; additionally keep the hand-rolled-fetch path as the documented fallback for check-in specifically, since it's the core transactional flow and cannot tolerate an unvalidated new failure mode from an alpha dependency. |
| **Not planned** | `users`, `loyalty` | `users` per §2's PII-exposure note needs its own query redesign before any adapter matters; `loyalty` has no urgency (§2) and can stay on the hand-rolled fetch path indefinitely. | N/A |

Each phase keeps the existing `@tanstack/react-db` + `packages/api-client` structure intact — only the sync strategy inside each `create<X>Collection` function changes. This is deliberately incremental at the *collection* level (matching how the codebase is already organized) rather than a per-screen or big-bang rewrite.

## 6. Risk register

- **RLS/authorization gap — the dominant risk, and larger than originally framed.** There is no backend service standing between the browser and Postgres for this data path; RLS is the entire authorization boundary. Everything else in this list is secondary until this is closed.
- **Realtime subscription cost/connection limits at scale.** Cannot be assessed from static analysis — Supabase's Realtime pricing and connection ceilings scale with concurrent client connections, which depends on real usage patterns. Given the phased plan defers Realtime-bearing collections (`attendance`) to phase 3, this risk is naturally deferred too.
- **Offline/optimistic-write conflict resolution.** TanStack DB's existing optimistic-mutation model (§1) already handles the common case (mutation applied locally, rolled back on server rejection); moving to the adapter doesn't inherently improve or worsen this unless Realtime introduces concurrent-edit scenarios (e.g., two staff members checking in the same attendee) that don't exist under the current one-shot-fetch model. Real design question specifically for phase 3, not before.
- **`@supabase-labs/tanstack-db` maturity.** Alpha, recently released, from a separate package (`@supabase-labs/tanstack-db`) layered on top of `@tanstack/react-db`, which is itself pre-1.0. Two early-stage dependencies stacked. This is a reason to keep phase 1 small, flag-gated, and reversible (§5) — not a reason to avoid evaluating it, since it's a purpose-built official adapter for exactly this app's data source and removes a meaningful amount of hand-written fetch/error-handling code (§1) if it holds up.
- **Multi-tenant scoping interaction with RLS.** Worth restating as its own risk: RLS policies that get the `org_memberships` join subtly wrong (e.g., allowing a `viewer` role to write, or leaking org B's data to an org A member through a badly-scoped join) are easy to write and hard to catch without dedicated tests — and this codebase currently has no test coverage anywhere to catch that class of regression. **Writing tests should be a prerequisite of phase 0, not an afterthought of phase 1.**

## "Don't migrate this" list

- **`users`** — needs a narrower, purpose-built query shape before any adapter matters (§2); moving the current shape onto live queries/Realtime would make an existing over-fetch worse, not better.
- **`loyalty`** — no realtime value, no urgency; leave on the hand-rolled fetch path indefinitely.
- **The anonymous-session mechanism itself** — this is Supabase Auth's job already; don't wrap it in a TanStack DB collection for architectural symmetry (§3).
- **Anything before phase 0's RLS prerequisite lands and is tested** — restated because it's the single most important scoping decision in this part, adapter or no adapter.
